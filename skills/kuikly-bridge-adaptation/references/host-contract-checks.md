# 宿主契约与验收

只在已有 Bridge/Module 与宿主联调、排查回调或导航问题时读本页。这里是检查框架，不是要求所有项目采用同一通道、超时或错误码。

## 一个方法的逐端登记

对每个**实际目标平台**各填一行；项目没有的平台不需实现。未实现不应假装验证通过。

| 平台 | Module 注册名/方法名 | 宿主读取的参数层级和类型 | 完成、取消、失败回调 | 线程/页面要求 | 证据 |
| --- | --- | --- | --- | --- | --- |
| Android | 待从宿主代码确认 | 待确认 | 待确认 | 待确认 | 代码位置、脱敏回包、运行记录 |
| iOS | 待从宿主代码确认 | 待确认 | 待确认 | 待确认 | 同上 |
| HarmonyOS | 待从宿主代码确认 | 待确认 | 待确认 | 待确认 | 同上 |

Kuikly 侧序列化要与宿主实际读取方式核对：对象被编码成 JSON 字符串、字符串内又有 `result` JSON、数字码被宿主写成字符串，这些都可能让“原生已成功”在业务侧变成解析失败。通过固定样本分别测对象、字符串、空值和异常格式，**只在协议适配层解码**。

## 回调与导航验收

1. 记录每次调用标识、方法名、页面标识以及宿主接收/完成事件。日志不含 Token、密钥或完整个人数据。
2. 成功、失败、取消各走一次；确认一次调用最多一次终态。对无回调的立即动作，先确认它究竟是 fire-and-forget 还是旧宿主遗漏了完成结果。
3. 并发发出 A、B，反序返回 B、A；结果必须回到各自调用方。若旧协议没有 requestId，检查框架 callback 是否已逐次关联，不能默认“先发先回”。
4. 页面关闭或容器退出后让旧回包抵达；不应更新已失活页面。需要常驻监听时，核查注册和解除路径，不把单次回调改成永久回调。
5. 画两层栈：宿主容器栈和 Kuikly 内部页栈。对子页返回记录关闭前栈顶、关闭后栈顶、上页恢复次数；旧 H5 关闭 WebView 不自动等于弹出 Kuikly 子页。

## 症状 → 第一定位点

| 症状 | 首先核对 | 避免的错误修复 |
| --- | --- | --- |
| 仅某个平台无响应 | 该平台 Module 是否注册、方法名是否匹配、失败分支是否回调 | 在页面默认为成功 |
| 原生日志成功，页面失败 | 返回对象/字符串层级、错误码类型、二次序列化 | 在页面到处尝试 `result.result` |
| 取消后一直 loading | 原生取消路径与超时责任方 | 固定延时合成成功 |
| 快速两次操作结果串位 | requestId 或框架 callback 的逐次关联 | 按回包顺序配对 |
| 子页返回退出整容器 | H5 容器关闭与 Kuikly 页栈 pop 的映射 | 只修改按钮文案 |
| 返回后弹过期提示 | 回调所属页面是否仍活跃、是否已消费 | 无条件写页面状态 |

交付结论分成“源码契约已核对”“转换样本通过”“目标平台编译通过”“真实宿主交互通过”。不能把 Demo mock 或单个平台成功写成所有宿主通过。
