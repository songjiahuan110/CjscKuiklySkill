# 旧能力到 Kuikly 的契约映射

需要迁移或排查某个方法时，为**该方法**填一张卡；不要把整个旧 Bridge 复制进页面。

| 字段 | 从哪里取得证据 |
| --- | --- |
| 业务动作与旧调用点 | 旧页面代码和触发条件；区分点击、页面恢复、自动重试 |
| 旧入口与宿主分发 | 桥接方法名、通道名、宿主 switch/handler；逐层定位 |
| 请求样本 | 脱敏后的原始调用参数，以及宿主实际读取的字段路径/类型 |
| 返回样本 | 成功、业务失败、网络失败、取消、无返回；记录对象还是 JSON 字符串 |
| 时序 | 同步/异步、是否可并发、回调是否多次、超时和取消责任方 |
| 页面归属 | 返回时原页面是否仍在、会改变哪个页面栈、谁负责恢复刷新 |
| 平台差异 | 每个目标平台的注册名、方法、线程和缺失分支 |

## 字节与层级对照

不要只比较反序列化后的业务字段。有旧链路可对照时，按需保存四处脱敏样本：旧调用原始入参、宿主收到的入参、宿主原始回包、Kuikly 适配后的结果；缺少其中一处要标明无法核对的边界。对每个字段标注 `string`、`number`、`boolean`、`null`、`object` 或“内层 JSON 字符串”。数字 `0` 与字符串 `"0"`、对象与 JSON 字符串、字段缺失与显式 `null` 不能擅自等同。

当协议确需兼容多种历史形态时，把识别顺序、接受条件和拒绝条件写成测试样本，解码集中在边界层。例如“`payload` 为对象”和“`payload` 为 JSON 字符串”是两条明确的输入用例，不应让页面到处尝试二次解析。

## 完成判据

- 相同输入在旧页面与 Kuikly 页面进入同一个宿主处理逻辑，或差异有明确设计依据。
- 成功、失败、取消各有可观察的终态；不把空结果当成功，也不对合法的 fire-and-forget 强造回调。
- 并发反序返回时调用与结果不会串位；页面离开后的旧结果不会写入新页面。
- 旧页面回归仍通过；未运行的平台明确列为未验证。
